**运行时类型（`runtime.type`）决定一次运行由谁的执行模型负责。正式值是三个——DSH 原生、Star Harness、Codex——另有一个 `native-engine` 只能被路由选中，不能创建。**

这一页讲清三个值各自的归属与能力、`native-engine` 这个陷阱、以及运行时之外那一层「执行策略」如何限制写入范围。

## 为什么运行时不是「引擎选项」

把运行时理解成「换个模型后端」会立刻遇到矛盾：同一份 Agent 定义，在三个运行时上的可用能力根本不同——有的支持重放，有的支持子任务，有的两者都不支持。这不是配置差异，是执行归属差异。

| 你想做的事 | 需要的前提 |
| --- | --- |
| 重放一次历史运行 | 运行时支持 `replay`（Codex 与 DSH 原生支持，Star Harness 不支持） |
| 让 Agent 拆出子任务 | 运行时支持 `child-tasks`（只有 Star Harness 支持） |
| 从历史事件恢复未完成的 turn | 运行时支持 `resume`（只有 Star Harness 支持） |
| 把 Agent 部署成常驻托管运行时 | 运行时可托管（只有 DSH 原生与 Codex 可以） |

所以选运行时不是风格偏好，它决定了后面能做哪些事。**运行时在创建时锁定，之后不能改**——换运行时只能新建一个 Agent。

## 3+1 陷阱

这是全站最容易写错的一处，因为它有两份都正确的清单：

| 清单 | 包含几个值 | 谁在用 |
| --- | --- | --- |
| 类型断言接受的运行时 | **4** 个（含 `native-engine`） | 路由层：本地会话可能被路由到独立引擎进程 |
| 创建表单列出的运行时 | **3** 个 | 用户界面：三个值都可见，但 Star Harness 在新建时带「未开放」徽章且不可选中 |

类型断言接受 4 个值，是因为本地 Star Harness 会话在满足条件时会被路由到 `native-engine` 进程上执行；创建表单只列出 3 个，因为 `native-engine` 的实验路径还没走到可创建的地步。

三个可见值里，**Star Harness 在新建时不可选**：按钮带「未开放」徽章并处于 `disabled` 状态（`src/client/pages/agent-form.mjs:265-267`）。编辑一个已经使用 Star Harness 的既有 Agent 时它是可选的，因为 `creatableRuntime` 对 `editing` 放行（`src/client/pages/agent-form.mjs:61`）。

<Callout type="warn" title="所以「支持 4 种运行时」是错的">
  创建表单里能看到 3 个，其中只有 2 个能在新建时选中。`native-engine` 是可路由值，不是可选项。写「4 种」会让读者在创建表单里找不到第四个选项。
</Callout>

历史文档里这个运行时还有两个别名——AgentKit Harness 与 Native Harness。**两个别名都已废弃**，统一写 **Star Harness**（`harness`）。

## 三个正式运行时

| 项 | DSH 原生 | Star Harness | Codex |
| --- | --- | --- | --- |
| 值 | `dsh-native` | `harness` | `codex` |
| 界面名称 | DSH Native Harness | Star Harness | Codex Agent |
| 执行归属 | DSH 自己 | KSADK Harness 原生内核 | Studio 内的 Codex App Server 适配器 |
| 执行模型 | `native` | `native-kernel` | `codex-app-server` |
| 契约 | `agentkit.studio.runtime/v1` | DSH 原生 turn 契约 | `studio.codex.adapter/v1` |
| 事件所有者 | DSH 会话 | 原生 run store | Studio Codex 适配器 |
| 流所有者 | `dsh-agent/assistant-stream` | `native-model-port` | `codex-turn/item` |
| 新建默认 | **是** | 否 | 否 |

<Diagram src="/assets/agentkit-runtime-ownership.png" alt="三个运行时在模型与工具循环、会话转录、持久运行状态、Studio 接缝四条泳道上的归属矩阵" />

*读图要点：执行者不是转录所有者——同一个运行时里，「谁在跑模型循环」和「谁在保存事件日志」是两个不同实体。四条泳道里只有 `cancel` 是三者共有的能力，其余能力都属于某一个实现，不能靠配置打开。*

## 能力矩阵

| 能力 | DSH 原生 | Star Harness | Codex |
| --- | :---: | :---: | :---: |
| `session` | ✅ | — | ✅ |
| `session-events` | ✅ | — | — |
| `stream` | ✅ | — | ✅ |
| `cancel` | ✅ | ✅ | ✅ |
| `replay` | ✅ | — | ✅ |
| `persistence` | ✅ | — | — |
| `build-binding` | ✅ | — | ✅ |
| `native-run` | — | ✅ | — |
| `durable-receipts` | — | ✅ | — |
| `tool-approval` | — | ✅ | — |
| `resume` | — | ✅ | — |
| `child-tasks` | — | ✅ | — |

只有 `cancel` 是三个运行时都支持的。能力项不是功能开关，不能通过配置打开——它是运行时实现的一部分。

## 运行时之外的硬规则

| 规则 | 允许的值 | 越界结果 |
| --- | --- | --- |
| 创建 Agent | 3 个正式值 | `RUNTIME_UNSUPPORTED` |
| 专家团角色 | 仅 DSH 原生、Star Harness | `TEAM_TEMPLATE_RUNTIME_UNSUPPORTED` |
| 专家团成员（运行时） | 仅本地 DSH 原生、Star Harness | `TEAM_AGENT_UNSUPPORTED` |
| 托管部署 | 仅 DSH 原生、Codex | 不出现在可部署列表 |
| 托管清单声明 | 3 个正式值 | `MANAGED_RUNTIME_IDENTITY_MISMATCH` |

「专家团不含 Codex 成员」与「托管部署不含 Star Harness」是两条独立限制，不要合并成一句「部分场景受限」。

## 执行策略：限制写入范围的那一层

运行时决定谁执行，执行策略决定**执行时能写哪里**。两者是正交的。

| 模式 | 排名 | 含义 | 默认 |
| --- | --- | --- | --- |
| `read-only` | 0 | 只读，不写工作区 | 无人值守运行的默认值 |
| `workspace-write` | 1 | 可写工作区 | **是**（云执行默认） |
| `danger-full-access` | 2 | 完全访问 | 是上限，不是默认 |

排名从最小权限到最大权限。三条硬规则：

1. **只能收窄，不能放宽**。请求的模式如果超出部署声明的上限，会被夹到上限值，而不是报错——这是为了让策略变更不影响已经发出的请求。
2. **上限默认是最高**。云执行的默认模式是 `workspace-write`，默认上限是 `danger-full-access`，所以默认情况下三种模式都可选。
3. **无人值守一律只读**。无人值守的执行策略是 `read-only` 加 `approvalPolicy: never`，且审批来源标记为运行时策略——没有人工可以批准，所以只能只读。

除权限模式外，策略里还有一个「审批策略」，取值只能是 `ask` 或 `never`。Star Harness 的 Agent 还额外带一份原生权限策略（模式 `strict` / `loose` / `custom`），它**只增加工具约束，不会授予任何宿主能力**。新建的 Star Harness Agent 默认是 `strict`。
