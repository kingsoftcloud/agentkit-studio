**The AgentKit Studio product model has exactly six nouns: agent, revision, build, session, run, and runtime type — the value that decides where those entities execute.**

This chapter takes each one in turn and states the hard constraints between them. When you finish, you can answer questions like "will changing this setting affect a session that is already running?" without trying it first.

## System layers

<Diagram src="/assets/agentkit-studio-overview.en.png" alt="AgentKit Studio five-layer architecture: browser UI, Studio control plane, Host service domains, runtime adapters and external kernels, with the /agentkit RPC and HTTP prefix channels" />

*How to read this: the browser only sends operation ids and holds no state; the Host service domains are the only persistence boundary; everything below the runtime adapters is an external kernel. Of the two physical channels, only `/agentkit` RPC goes through the 134-operation dispatcher — model proxying and conversation streaming use HTTP prefix routes instead.*

## Why a concepts chapter exists

The four panels each expose one slice of the product model, yet the same vocabulary appears together on the same screen:

| What the UI shows | The concept behind it | Most often mistaken for |
| --- | --- | --- |
| A notice that saving produced a new revision | Revision | A draft you can overwrite |
| A build record in the operations panel | Agent build | A CI or image build |
| A row in the agent list | Agent | A running process |
| An entry in the session list | Session | A log of one request |
| Usage and duration at the bottom | Run | A cumulative total for the session |

Treating a revision as an overwritable draft, or a build as a pipeline artifact, leads to the same wrong conclusion: that editing configuration changes a session already in flight. It does not. Not because the product lacks hot reload, but because these four entities freeze at different layers — see [Agent · Revision · Build · Run](./agent-revision-build.mdx).

The four panels and their secondary tabs are organised like this:

<Diagram src="/assets/agentkit-workbench-map.en.png" alt="Workbench map: the browser UI splits into Overview, Agents, Resources and Operations, with each panel's second-level tabs and their responsibility" />

*How to read it: the four panels are peers, not a hierarchy. What decides where a run executes is the agent's runtime type, not the panel.*

The five tabs under Operations are not five sections of one page — they are five independent surfaces: builds and deployments own artifacts, automation owns schedules, evaluation owns pass rates, observability owns traces, and Channels owns remote channels. They share no selection state, so switching tabs never changes which Agent you are looking at.

## What each of the six entities owns

| Entity | Primary key | What it freezes | Who owns its lifecycle |
| --- | --- | --- | --- |
| Agent | `agentId` | Only a "current pointer" | Studio local store |
| Revision | `revision` | A complete immutable snapshot after one edit | The agent; append-only |
| Agent build | `buildId` | A content-addressed package of one revision plus its execution engine | The agent; rebuildable |
| Session | `sessionId` | One durable DSH event journal | The Host |
| Run | `runId` | One turn from start to end | The session |
| Runtime type | `runtime.type` | Which execution model serves this agent | Locked when the agent is created |

Studio neither generates nor stores the last two identifiers (`sessionId`, `runId`). It only validates that their binding is correct. A mismatched binding is an error, never a guess.

## How the concepts relate

```text
Agent agentId
  └─ Revision revision 1..N        (immutable; saving appends)
       └─ Agent build buildId       (content-addressed; same input, same id)
            └─ Session sessionId    (DSH owns the journal)
                 └─ Run runId       (one turn)
```

A complete run identity needs all five fields: `agentId`, `revision`, `buildId`, `sessionId`, `runId`. Missing one is rejected rather than degraded to a partial identity. The same rule implies: **an agent without a build can still converse, but without a build there is no reproducible run identity.**

## The four runtimes

`runtime.type` has exactly three values, and they are `STUDIO_RUNTIME_TYPES` (`src/runtime-contract.mjs:6`):

| Value | UI name | Creatable | Execution model |
| --- | --- | --- | --- |
| `dsh-native` | DSH Native Harness | Yes (default for new agents) | `native` |
| `harness` | Star Harness | Conditionally: installed + enabled + a usable workspace | `native-kernel` |
| `codex` | Codex Agent | Yes | `codex-app-server` |
| `ksxc` | KSXC | When an approved release is installed and enabled | `ksxc-app-server` |

Star Harness is the only pluggable one of the three: it is delivered as npm packages from ksadk-harness and only appears in the creation form once it is installed and bound to a workspace. See [the three runtimes](./runtimes.mdx).

## Five bindable resource kinds

Resources are not an appendix to the concepts chapter; they explain why the same prompt behaves differently in two environments:

| kind | UI label | Source | How many per agent |
| --- | --- | --- | --- |
| `model` | Model | Local model profiles plus the model gateway | Many, one of them default |
| `mcp` | MCP | Local MCP catalog plus the cloud catalog | Many |
| `skill` | Skill | Installed Skills plus cloud Skill Spaces | Many |
| `knowledge-base` | Knowledge base | Cloud control plane | One |
| `memory-instance` | Memory | Cloud control plane | One |

Bindings live on the revision, so **changing resources means changing the revision**. Credential values never enter a revision — see [Resources and bindings](./resources.mdx).
