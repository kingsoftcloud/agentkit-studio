**AgentKit Studio 的产品模型只有六个名词：智能体（agent）、修订版本（revision）、Agent 构建（build）、会话（session）、一次运行（run），以及决定这些实体在哪执行的运行时类型（runtime type）。**

这一章逐个讲透它们，并给出它们之间的硬性约束。读完这一章你可以自己回答「改一个配置会不会影响已经在跑的会话」这类问题，而不必先试一次。

## 系统分层

<Diagram src="/assets/agentkit-studio-overview.png" alt="AgentKit Studio 五层架构：浏览器 UI、Studio 控制面、Host 服务域、运行时适配层与外部内核，以及 /agentkit RPC 与 HTTP 前缀两条物理通道" />

*读图要点：浏览器只发 operation id，不持有任何状态；Host 服务域是唯一持久化边界；运行时适配层之下全部是外部内核。两条物理通道里，只有 `/agentkit` RPC 会经过 134 个 operation 的分发器，模型代理与对话流走的是 HTTP 前缀路由。*

## 为什么需要概念层

四个面板各自只暴露产品模型的一部分，同一批术语却在同一个屏幕上交叉出现：

| 你在界面上看到的 | 它背后的概念 | 最容易被误解成 |
| --- | --- | --- |
| 保存后提示生成了新的修订版本 | 修订版本 | 可以被覆盖的草稿 |
| 运行中心里的构建记录 | Agent 构建 | CI 构建或镜像构建 |
| 智能体列表里的一行 | 智能体 | 一个正在运行的进程 |
| 会话列表里的一条历史 | 会话 | 一次请求的日志 |
| 底部显示的用量与耗时 | 一次运行 | 整个会话的累计量 |

把修订版本当成可覆盖的草稿，或者把构建当成流水线产物，都会导向同一个误判：以为改完配置，正在跑的会话会跟着变。事实是**都不会变**。原因不是产品「没做热更新」，而是这四个实体各自冻结在不同层次上，见[Agent · Revision · Build · Run](./agent-revision-build.mdx)。

四个面板与它们的二级标签是这样组织的：

<Diagram src="/assets/agentkit-workbench-map.png" alt="工作台地图：浏览器 UI 下分总览、智能体、资源库、运行中心四个面板，每个面板下的二级 tab 及其职责" />

*读图要点：四个面板是并列的，没有从属关系；真正决定「这次运行在哪跑」的是 Agent 的运行时类型，不是面板。*

「运行中心」的五个标签不是一个页面的五个分区，而是五个独立的工作面：构建与部署管产物，自动化管定时，评测管通过率，观测管 Trace，Channels 管远端渠道。它们之间没有共享的选中状态——切换标签不改变你正在看的是哪个 Agent。

## 六个核心实体的分工

| 实体 | 主键 | 冻结了什么 | 生命周期由谁拥有 |
| --- | --- | --- | --- |
| 智能体 | `agentId` | 只拥有一份「当前指向」 | Studio 本地存储 |
| 修订版本 | `revision` | 一次编辑后的完整不可变快照 | 智能体，只增不改 |
| Agent 构建 | `buildId` | 某个修订版本加执行引擎的内容寻址包 | 智能体，可重复构建 |
| 会话 | `sessionId` | 一条 DSH 持久事件日志 | 宿主（Host） |
| 一次运行 | `runId` | 一个 turn 从开始到结束 | 会话 |
| 运行时类型 | `runtime.type` | 这次运行由谁的执行模型负责 | 智能体创建时锁定 |

后两个标识（`sessionId`、`runId`）不由 Studio 生成，也不由 Studio 存储。Studio 只校验它们的绑定关系是否正确——绑定对不上就是错误，不会「尽量猜一个」。

## 概念之间的关系

```text
智能体 agentId
  └─ 修订版本 revision 1..N        （不可变，保存即新增）
       └─ Agent 构建 buildId        （内容寻址，同一输入只有同一个 id）
            └─ 会话 sessionId       （DSH 拥有日志）
                 └─ 一次运行 runId  （一个 turn）
```

一次运行的完整身份必须五个字段齐全：`agentId`、`revision`、`buildId`、`sessionId`、`runId`。缺一个就拒绝，而不是降级成「部分身份」。这条规则同时意味着：**没有构建的智能体也能对话，但没有构建就没有可复现的运行身份**。

## 四种运行时

`runtime.type` 支持四个值，就是 `STUDIO_RUNTIME_TYPES`（`src/runtime-contract.mjs:6`）：

| 值 | 界面名称 | 可以创建 | 执行模型 |
| --- | --- | --- | --- |
| `dsh-native` | DSH Native Harness | 是（新建默认） | `native` |
| `harness` | Star Harness | 条件可创建：已安装 + 已启用 + 有可用工作区 | `native-kernel` |
| `codex` | Codex Agent | 是 | `codex-app-server` |
| `ksxc` | KSXC | 已安装并启用审定版本 | `ksxc-app-server` |

Star Harness 由 ksadk-harness 的 npm 包提供，安装并绑定工作区后即可创建。KSXC 在 Studio 设置中管理版本与企业账号。见[四种运行时](./runtimes.mdx)。

## 五类可绑定资源

资源不是概念章的附注，它决定了「同一个提示词为什么在两个环境里表现不同」：

| kind | 界面标签 | 来源 | 每类可绑几个 |
| --- | --- | --- | --- |
| `model` | 模型 | 本地模型配置 + 模型网关 | 多个，其中一个默认 |
| `mcp` | MCP | 本地 MCP 目录 + 云端目录 | 多个 |
| `skill` | Skill | 已安装 Skill + 云端 Skill Space | 多个 |
| `knowledge-base` | 知识库 | 云端控制面 | 一个 |
| `memory-instance` | 记忆库 | 云端控制面 | 一个 |

绑定写在修订版本上，所以**换资源等于换修订版本**。凭证值本身从不进修订版本，见[资源与绑定](./resources.mdx)。
