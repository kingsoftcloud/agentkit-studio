## 渠道与持久化联调

使用 Studio Host 的渠道编排创建独立 Mock 渠道，目标为上述 Harness 云端部署，
`ConnectorWorkspaceId` 为空。首轮合成事件经真实 Channel InboundPipeline、Channel API、
Server RunAgent 和云端模型完成回复；再次替换 Agent 容器并核对新实例 ID 后，通过相同
渠道 peer 发第二轮消息，找回首轮暗号并保留冻结系统前缀。每轮把同一个事件提交两次，
Mock 平台出口各只有一条回复。测试没有把第一轮内容重新放入第二轮用户消息。

这验证了渠道绑定、去重与 Agent 持久化历史的衔接；MockAdapter 代替真实平台收发，
不能据此宣布 WPS/飞书消息验收通过，也不证明正在执行的事件能跨进程自动接管。

## 删除后的存储回收核对

独立查询 Runtime Service 确认上述三个持久化验收 Agent，以及定时投递验收 Agent
`ar-20261009033257-13f4b643`，均为 `DELETED`，且属于同一预发算力集群。
随后直接查询该集群：四个 runtime ID 对应的 Namespace、PVC 和 PV 均不存在。
这是实际 Kubernetes 存储对象回收证据，不依赖 GetAgent 的 404；云存储后端回收完成时间和
最终账单结算仍未核验。

检查同时发现 Server 的删除错误路径会在下游拒绝或超时后继续逻辑删除，甚至把任意
`not found` 文本解释为 runtime 不存在。修复要求收到匹配 runtime ID 的有效回执，或明确的
runtime-not-found 错误码；否则保留 Agent、凭证、产物和监控，返回失败供状态核对。
可选产物删除移到运行时删除受理之后。225 项相关回归通过，含真实 SQLite 持久化断言；
故障用例属于注入验证，不代表预发真实发生过这些故障。

修复后的 Server 两副本已更新并逐文件核对，镜像为
`sha256:ad67e1226b8d6f14addbad5db314016fd562ce4506a29a638c33be455003225b`。
基于预发现有源码叠加删除修复，保留较新的欠费回收与操作互斥逻辑；隔离 Python 进程中
10 个故障/成功场景通过，没有写共享数据库或调用真实删除。

随后使用已核验子账号经 KOP 创建独立 Agent `ar-20261009040649-cc12112b`，确认运行就绪、
20 GiB PVC Bound，并保存对应 PV 的 UID 与 `Delete` 回收策略。从真实 Studio 浏览器中
点击删除并确认，页面显示已删除；随后核对该 Namespace、PVC 和同一个 PV 均已消失。
PV 曾在页面删除完成后短暂保留，没有强删 finalizer 或手工删除卷。私有冻结运行包也已
校验归属后清除并确认下载返回 404。此次真实链路覆盖正常删除，错误分支仍由故障注入证明。
