# 补丁治理与宿主兼容

阶段 5A 增加机器清单及构建门禁，当前正在验证；阶段 5B 产品配置接口和 5C 维护来源收敛尚未完成。生产基线保持 DSH `639ed015397290b3745d163aafe02ffee4aa3f84`；通过行为对照移除 021 后剩余 32 项，其余补丁的内容和相对顺序不变。

## 变更入口

`patches/dsh-v0.2.0-rc.2/manifest.json` 列出每项补丁的类别、固定基线、SHA-256、修改文件及所属包、依赖、合同、风险、维护角色、上游状态、删除条件和验证方式。修改补丁时同时评审这些字段。清单中的验证要求是待运行场景，不能用登记记录代替通过证据。

同一文件的后续补丁必须通过依赖链声明前一个修改者，避免隐含的文件应用顺序。门禁拒绝依赖成环、依赖晚于使用者、混用基线、遗漏修改文件、未登记的补丁和内容摘要变化。桌面打包在克隆和运行工具前执行同一门禁。

上游状态区分 `not-submitted`、`pending`、`merged-unreleased` 和 `in-baseline`。没有核验提交或合入回执时使用 `unverified`，不能把它当作尚未提交或已合入。核验后记录对应提交或 PR；删除前还要验证当前产品基线具备等价行为。

## 构建与验证

```sh
make patch-manifest-check
make verify-patched-host DSH_ROOT="<固定 DSH checkout>"
```

后一命令在输出目录创建并锁定独立 checkout，从固定 Git commit 应用清单中的补丁。应用后的源文件 diff 必须与清单中的完整指纹一致；然后安装冻结依赖，构建官方 Web/Host，运行清单登记的受影响宿主测试。测试路径作为参数传给 Vitest，不执行清单中的命令文本。构建结束再次检查源码指纹，报告记录实际通过、失败及跳过数量。

CI 的 `patched-dsh-host` 使用相同入口，在 PR 和 main 提交上分别运行标准 Linux、Windows runner，并保留构建和测试报告。Web、Electron、生命周期、冻结 Build、平台打包和真实安装更新仍分别验收；宿主单元测试不能代替这些结果。

## 后续收敛

新宿主门禁首次运行时，33 个受影响测试文件中 32 个通过；`main-startup.spec.ts` 有 6 个更新动作失败。021 把官方 `updates.open()` 一律变成手动检查，而官方状态机本来已在空闲和检查失败时强制刷新。恢复官方默认后，该文件 114 项测试全部通过，保留已有可用更新的下载、已下载更新的安装及手动检查行为。删除记录进入清单，原失败报告与对照结果保存在忽略的 `stage-5/` 证据目录。它证明 Electron main 的受控行为测试，不能代替真实安装更新。

移除后的干净隔离 checkout 再次完成官方 Web/Host 构建；33 个登记测试文件中 872 项通过、0 失败，1 项 Windows 路径大小写场景在本地 macOS 跳过，交给 Windows CI 复核。Studio 全量 912 项源码测试、公开面、当前快照及历史凭证扫描和 515 文件的实际 tarball 检查通过。浏览器和 Host 生产模块未随本批清单工具改变；阶段 4 的平台包证据仍对应其已记录的 33 补丁输入，32 补丁的最终平台及安装更新验收留在后续收敛门禁中。

产品名称、版本、App ID、更新源、默认 bundle 和平台输入将在 5B 归入同一产品配置接口，并验证默认 DSH 及已有 Profile 的禁用选择。通用修复和会话持久化扩展保持独立评审。5C 固定维护分支并自动导出补丁，避免分支与 patch 文件成为两套修改来源。

候选升级只在独立 checkout 演练，保留应用冲突、等价行为检查和耗时。候选检查失败不切换生产基线，不据此删除补丁。
